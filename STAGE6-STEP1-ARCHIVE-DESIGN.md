# Stage 6 — Step 1: Character and World Archive Design

## 1. Scope and safety boundary

This document defines the proposed data contract and user interface for the character/world archive. It is a design specification only.

- No SQL has been executed.
- No Supabase project, table, policy, bucket, or setting has been modified.
- No credentials or project secrets are included.
- The existing `characters.html` remains a static showcase until a later implementation step is approved.
- The legacy `supabase-schema.sql` and `supabase-schema.v2.sql` do not implement this design and must not be executed as a substitute for a reviewed V3 schema.

## 2. Product goals

The archive should support five connected capabilities:

1. Create and maintain character profiles.
2. Create and maintain worldbuilding entries, including worlds, regions, species, factions, systems, rules, locations, and historical events.
3. Link characters and worldbuilding entries to each other and to existing works.
4. Preserve immutable revision history and restore an earlier revision as a new revision.
5. Upload and manage character artwork, portraits, maps, and reference images with alternative text and publication-aware access.

The initial editor is intended for the site owner/authorized administrators. Public visitors can read published records only. Public self-registration does not grant archive-editing privileges.

## 3. Proposed pages and interaction model

### 3.1 Public pages

- `characters.html`: published character index; search by name/alias; filter by work, world, and tags; sort by recently updated or name. Draft and archived records are never included.
- `worlds.html` (new): published worldbuilding index; filter by entry type, parent region/world, and associated work.
- `character-detail.html` (new): one published character, portrait/gallery, profile sections, related characters, linked world entries, and works.
- `world-detail.html` (new): one published world entry, structured sections, child entries, related entries, linked characters, and works.

A public card should navigate to a detail page. It must not open an edit form. The public pages must not expose drafts through guessed IDs, search, relation panels, or image URLs.

### 3.2 Creator-only management page

- `archive-admin.html` (new): creator workspace with tabs for Characters, World Entries, Relations, Media, and Revision History.
- List view: search, type/status filters, pagination, status indicator, last-updated time, and actions to edit, preview, duplicate, or archive.
- Editor view: grouped form sections, related-record picker, image uploader, draft preview, validation messages, and explicit Save Draft / Publish / Unpublish / Archive controls.
- The page must verify the signed-in user's admin status through a trusted database function and then rely on database row-level security (RLS) for actual authorization. Hiding controls in JavaScript is not security.
- If the user is signed out or not an administrator, show a clear access-denied state and do not render editable data.

### 3.3 Editing interaction rules

- Use explicit saves for the first release; do not imply autosave unless it is implemented and tested.
- Warn before navigating away with unsaved changes.
- Validate required fields before saving and show field-level errors.
- Use a unique slug per table; suggest a slug from the title but allow manual editing.
- Use a concurrency token (`lock_version`) so a stale editor cannot silently overwrite newer changes.
- Archive by default instead of hard-deleting. Permanent deletion is a separate, administrator-only action with a strong confirmation and reference checks.
- Restoring a revision creates a new revision from the selected snapshot; it does not erase later history.

## 4. Proposed data model

All identifiers, table names, column names, function names, storage paths, and technical logs use English/numbers. Chinese remains allowed in user-facing labels and content.

### 4.1 `ip_characters`

One row per character.

| Field | Type | Rules / purpose |
|---|---|---|
| `id` | `uuid` | Primary key, generated by database |
| `slug` | `text` | Required, unique, URL-safe, lowercase; immutable in public URLs only if product chooses that rule |
| `name` | `text` | Required, 1–160 characters |
| `aliases` | `text[]` | Optional alternate names/transliterations |
| `summary` | `text` | Short public synopsis, max 1,200 characters |
| `profile` | `jsonb` | Structured profile document, schema-versioned; includes appearance, personality, background, abilities, identity details chosen by creator, and other optional sections |
| `tags` | `text[]` | Search/filter labels |
| `status` | `text` | `draft`, `published`, or `archived`; default `draft` |
| `cover_media_id` | `uuid` | Optional reference to primary portrait in `ip_media` |
| `sort_order` | `integer` | Optional manual ordering |
| `created_by` | `uuid` | References `auth.users(id)`; set by trusted server/database context |
| `updated_by` | `uuid` | References `auth.users(id)`; set by trusted server/database context |
| `created_at` | `timestamptz` | Database-generated creation time |
| `updated_at` | `timestamptz` | Database-maintained update time |
| `published_at` | `timestamptz` | Null until first publish; preserve on ordinary edits unless explicitly republished by policy |
| `lock_version` | `integer` | Starts at 1; increments on each successful update to prevent stale writes |

Constraints/indexes: unique `slug`; allowed status values; nonblank trimmed `name`; GIN indexes for `aliases`/`tags` only if search workload justifies them; indexes for `status`, `updated_at`, and `cover_media_id`.

### 4.2 `ip_world_entries`

One row per worldbuilding entry. This unified table supports multiple entry types without a new table for every lore category.

| Field | Type | Rules / purpose |
|---|---|---|
| `id` | `uuid` | Primary key |
| `slug` | `text` | Required, unique, URL-safe |
| `title` | `text` | Required, 1–180 characters |
| `entry_type` | `text` | `world`, `region`, `species`, `faction`, `system`, `rule`, `location`, `event`, or `other` |
| `summary` | `text` | Short synopsis, max 1,500 characters |
| `body` | `jsonb` | Versioned structured rich-text document; supports headings, paragraphs, lists, quotations, links, and selected images |
| `metadata` | `jsonb` | Optional type-specific structured facts; validate allowed keys per entry type in application and later database constraints/functions where appropriate |
| `tags` | `text[]` | Optional search/filter labels |
| `parent_entry_id` | `uuid` | Nullable self-reference for hierarchy; prevent self-parenting and cycles |
| `status` | `text` | `draft`, `published`, or `archived`; default `draft` |
| `cover_media_id` | `uuid` | Optional reference to primary cover/map |
| `sort_order` | `integer` | Optional manual ordering |
| `created_by` | `uuid` | References `auth.users(id)` |
| `updated_by` | `uuid` | References `auth.users(id)` |
| `created_at` | `timestamptz` | Database-generated |
| `updated_at` | `timestamptz` | Database-maintained |
| `published_at` | `timestamptz` | Null until first publish |
| `lock_version` | `integer` | Optimistic concurrency control |

Constraints/indexes: unique `slug`; valid `entry_type` and `status`; `parent_entry_id <> id`; index `entry_type`, `status`, `parent_entry_id`, `updated_at`, and `cover_media_id`. Cyclic parent chains must be rejected by a later reviewed database function/trigger, not only by the UI.

### 4.3 `ip_character_relations`

Stores a typed relationship between two characters.

| Field | Type | Rules / purpose |
|---|---|---|
| `id` | `uuid` | Primary key |
| `character_id` | `uuid` | Required FK to `ip_characters` |
| `related_character_id` | `uuid` | Required FK to `ip_characters`; cannot equal `character_id` |
| `relation_type` | `text` | Required controlled value such as `family`, `romantic`, `friend`, `rival`, `mentor`, `protector`, `ally`, `enemy`, or `other` |
| `label` | `text` | Optional creator-defined relationship label |
| `description` | `text` | Optional relationship context |
| `is_directional` | `boolean` | Whether the relationship is directional; default false |
| `status` | `text` | `draft` or `published`; publication visibility must require both related characters to be published |
| `created_by` | `uuid` | Creator identity |
| `created_at` | `timestamptz` | Database-generated |
| `updated_at` | `timestamptz` | Database-maintained |

Prevent duplicate identical relationship rows according to a documented normalization rule. Public reads must never reveal a draft character's name or ID through relation records.

### 4.4 `ip_character_world_links`

Connects characters to world entries.

| Field | Type | Rules / purpose |
|---|---|---|
| `id` | `uuid` | Primary key |
| `character_id` | `uuid` | Required FK to `ip_characters` |
| `world_entry_id` | `uuid` | Required FK to `ip_world_entries` |
| `link_type` | `text` | E.g. `origin`, `resides_in`, `member_of`, `uses_system`, `created_by`, `affected_by`, or `other` |
| `notes` | `text` | Optional link context |
| `status` | `text` | `draft` or `published` |
| `created_by` | `uuid` | Creator identity |
| `created_at` | `timestamptz` | Database-generated |

Public visibility requires the link and both endpoint records to be published. Add uniqueness on the endpoint pair plus `link_type`.

### 4.5 `ip_character_work_links` and `ip_world_work_links`

These join tables connect archive records to the existing V3 `public.works` table.

Shared fields:
- `id uuid` primary key
- `character_id uuid` or `world_entry_id uuid` (required FK)
- `work_id uuid` (required FK to `public.works(id)`)
- `link_type text` (e.g. `appears_in`, `main_setting`, `mentioned_in`, `inspired_by`, `other`)
- `notes text` (optional)
- `status text` (`draft` or `published`)
- `created_by uuid`, `created_at timestamptz`

Public queries must expose a link only if the archive record and linked work are published and the link itself is published. Unpublished work titles must not leak through these join tables.

### 4.6 `ip_character_versions` and `ip_world_entry_versions`

Two version tables keep foreign-key integrity while storing immutable snapshots.

Shared fields:
- `id uuid` primary key
- `character_id uuid` or `world_entry_id uuid` (required FK)
- `version_number integer` (starts at 1 and unique per parent record)
- `snapshot jsonb` (full content snapshot, including fields needed to reconstruct the record; excludes secrets and access tokens)
- `change_summary text` (optional, max 500 characters)
- `changed_by uuid` (authenticated actor)
- `created_at timestamptz` (database-generated)
- `source_version integer` (optional version restored/copied from)

Version rows are append-only for client roles. Updates/deletes are denied to clients, including administrators through ordinary client APIs. A trusted database function or server-side administrative path will be needed for controlled restore operations. Every successful content save should create the content update and snapshot atomically, preferably through a reviewed RPC/transaction so no record update can succeed without its version row.

### 4.7 `ip_media`

Metadata for uploaded artwork and images. Actual file bytes live in a private Supabase Storage bucket, proposed name `ip-assets`.

| Field | Type | Rules / purpose |
|---|---|---|
| `id` | `uuid` | Primary key |
| `storage_path` | `text` | Required unique object path; generated from owner/entity UUIDs, not user-provided paths |
| `original_filename` | `text` | Sanitized display-only filename |
| `mime_type` | `text` | Allowlist: JPEG, PNG, WebP, AVIF; reject SVG and executable/unknown formats initially |
| `byte_size` | `bigint` | Positive and within configured upload limit |
| `width` / `height` | `integer` | Optional verified image dimensions |
| `alt_text` | `text` | Required before public publication; accessibility description |
| `caption` | `text` | Optional caption/credit |
| `status` | `text` | `draft`, `published`, or `archived` |
| `uploaded_by` | `uuid` | References `auth.users(id)` |
| `created_at` | `timestamptz` | Database-generated |

Use join tables `ip_character_media` and `ip_world_entry_media` with `media_id`, parent record ID, `media_role` (`cover`, `portrait`, `gallery`, `map`, `reference`), `sort_order`, `caption_override`, and `created_at`. This allows one media item to be linked safely to more than one approved record without polymorphic foreign keys.

Storage access must be private by default. Draft media is administrator-only. Published media may be served through short-lived signed URLs generated only after checking that its media row and at least one authorized public parent are published. Storage path guessing must not grant access. Define upload byte/pixel limits, per-user quotas, orphan cleanup, and delete policy before implementation.

## 5. Permission model

### Public/anonymous visitors (`anon`)

- Read only `published` character and world entries.
- Read only published relations/links whose every endpoint is also published.
- Read public image metadata and access only to approved published media delivery.
- Cannot insert, update, archive, publish, restore, or delete archive content, relationships, revisions, or media.

### Signed-in readers (`authenticated`, not administrator)

- Same public read access as anonymous visitors.
- No archive write access. Signing in does not imply creator privileges.
- Cannot assign their own role or change `created_by`, `updated_by`, `uploaded_by`, status, or version numbers.

### Creator/admin

- Read all draft, published, and archived archive records.
- Create and edit characters, world entries, links, and media metadata.
- Publish/unpublish/archive records and create new revisions.
- Restore a previous snapshot only through a trusted, audited operation that creates a new revision.
- Hard deletion is restricted and requires reference checks and explicit confirmation.

### Database enforcement

- Enable RLS on every new table.
- Revoke broad table privileges first, then grant only the required operations.
- Policies must call a reviewed trusted admin helper compatible with the V3 frontend (the frontend currently expects `public.is_admin()`); never trust a role value supplied by JavaScript.
- Public read policies must check publication status at the database layer, not only in the page code.
- Protect immutable version rows with insert-only policies or trusted functions.
- Use foreign keys, unique constraints, check constraints, and indexes to enforce integrity.
- Audit role changes and privileged publication/restore operations.
- Do not expose service-role keys in browser code.

## 6. Structured content format

Character `profile` and world-entry `body` use versioned JSON documents rather than unrestricted HTML. Proposed document envelope:

- `type`: `doc`
- `schema_version`: integer, initially `1`
- `content`: ordered block array

Allowed block types for the first version: `paragraph`, `heading`, `blockquote`, `bullet_list`, `ordered_list`, `divider`, and `image`. Inline nodes support plain text plus `bold`, `italic`, `underline`, and `link` marks. Links must be HTTPS or safe relative paths; reject `javascript:`, `data:`, and unknown protocols. Image blocks reference an `ip_media.id`, not an arbitrary external URL. Validate JSON shape before saving and sanitize again when rendering.

Keep structured character fields (e.g. name, aliases, summary, tags) separate from the long-form document so search and relations do not depend on parsing rich text.

## 7. Save and publication workflows

### Create a draft

1. Administrator opens the creator workspace and selects New Character or New World Entry.
2. UI creates an unsaved form; no database row is written until the first explicit save.
3. Client validates required fields and safe content structure.
4. Database rechecks authorization, uniqueness, constraints, and owner fields.
5. Record is saved as `draft`; revision 1 is created atomically; `created_by`, `updated_by`, timestamps, and `lock_version` are set by trusted logic.
6. UI shows the saved draft ID/status and a link to preview it in an admin-only preview route.

### Update a draft or published record

1. Load record with its `lock_version`.
2. User edits and clicks Save Draft/Save Changes.
3. Update succeeds only if the stored version matches the editor's version; otherwise show a conflict and offer reload/compare, never silently overwrite.
4. Save content and append the next immutable revision in one transaction.
5. Preserve `published_at` on ordinary edits unless the explicit publication policy says otherwise.

### Publish

1. Validate name/title, slug, summary, body/profile schema, relation targets, image accessibility text, and linked works.
2. Show a preview and a summary of linked public items.
3. Publish only when all required validation passes.
4. Database checks admin permission and related-record visibility; sets status and `published_at`.
5. Public indexes and detail pages query published records only.

### Unpublish or archive

- Unpublish returns a record to `draft`; public pages must stop exposing it immediately.
- Archive sets `status = 'archived'`; preserve revision history and relationships for recovery.
- Public links and relation panels must omit archived/draft endpoints even if join rows remain.

### Restore a revision

- Admin selects a prior revision, sees a diff/preview, and confirms.
- The system copies the chosen snapshot into the current record and creates a new revision with a restore summary.
- Existing revision rows are never modified or deleted.

### Upload media

1. Validate file type, size, dimensions, and user permission.
2. Upload to a private temporary or entity-scoped object path.
3. Create `ip_media` metadata and parent link only after upload succeeds.
4. On metadata failure, delete the unlinked object or enqueue orphan cleanup.
5. Require alt text before publishing an image.
6. Do not delete an image still referenced by a published record.

## 8. Search, indexes, and validation

- Exact lookup: unique slug.
- List filtering: `status`, `entry_type`, `updated_at`, parent entry, and linked work.
- Search initially uses PostgreSQL text search over character name/aliases/summary and world title/summary/body text extracted in a controlled way. Add `pg_trgm` or external search only if measured needs justify it.
- Paginate all list queries; do not fetch the full archive at once.
- Avoid broad GIN indexes until query patterns and expected record volume are tested.
- Add check constraints for allowed status/type values and nonblank titles.
- Validate parent hierarchy cycles, duplicate relations, and publication endpoint consistency.

## 9. Error states and accessibility

- Signed out: prompt to sign in, without exposing draft data.
- Signed in but not admin: explain that archive editing requires creator permission.
- Network error: preserve unsaved form state in memory and offer retry; do not falsely claim the record was saved.
- Revision conflict: explain that another edit exists and offer reload/compare.
- Upload error: keep form data, report which file failed, and allow retry.
- Empty results: show a clear empty state and a New Record action only for administrators.
- Keyboard access, visible focus, labels for all fields, accessible dialogs, and required alt text are part of acceptance criteria.

## 10. Implementation sequence after this design is approved

1. Approve this data contract and UI behavior.
2. Draft a separate V3 SQL specification/migration for review only; do not execute it automatically.
3. Implement admin-only UI with mocked/local test data if useful, clearly labelled as non-persistent.
4. Review SQL, RLS, grants, storage policies, revision atomicity, and migration/rollback plan.
5. Only after explicit authorization, apply to a dedicated test Supabase project and run permission tests.
6. Connect the UI to the test backend and verify create/edit/publish/unpublish/relations/media/revision flows.
7. Deploy public pages only after end-to-end and security checks pass.

## 11. Acceptance checklist

- [ ] Admin can create, edit, save, preview, publish, unpublish, and archive a character.
- [ ] Admin can create, edit, save, preview, publish, unpublish, and archive a world entry of each supported type.
- [ ] Character-to-character, character-to-world, and archive-to-work links can be managed and filtered.
- [ ] Every successful save creates a new immutable revision in the same transaction.
- [ ] Revision restore creates a new revision and leaves old history unchanged.
- [ ] Image uploads are validated; draft media is not publicly readable; published images have alt text.
- [ ] Public queries cannot reveal draft/archived rows or their titles through relations, search, IDs, or media.
- [ ] Non-admin users cannot write archive tables or change ownership/status/version fields.
- [ ] Stale writes are detected; no silent overwrite occurs.
- [ ] Search/filter/pagination and keyboard accessibility pass browser testing.
- [ ] No SQL execution or Supabase change occurs without explicit user authorization.
